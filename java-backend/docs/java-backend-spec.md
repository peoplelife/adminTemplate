# Java Backend 项目规范

版本：1.2.0
适用范围：`java-backend` 及其测试、配置、接口文档
维护方式：项目规则由根目录 `AGENTS.md` 触发；本文件是详细规范。
更新日期：2026-10-28

## 1. 目的与优先级

本规范用于约束 AI 和开发者在本项目中的新增代码、接口变更和缺陷修复。项目已有的接口契约和数据库兼容性优先于通用模板或第三方 Skill。

规则按风险分级：

- **P0 必须遵守**：安全、鉴权、数据完整性、事务、SQL 注入、资源释放、错误处理。违反时必须修复或明确报告。
- **P1 新代码必须遵守**：分层、DTO、接口契约、测试、配置边界。遗留代码只在被修改的范围内逐步对齐。
- **P2 建议遵守**：命名、注释、格式和小型重构。不得为了 P2 规则制造大范围 diff。

## 2. 项目基线

- Java 21。
- Spring Boot 3.5.6、Spring MVC、Spring Security 6、Maven。
- MyBatis-Plus 3.5.12；生产数据库为 MySQL，测试默认使用 H2 的 MySQL 兼容模式。
- JWT 使用 JJWT HS256；接口文档使用 springdoc OpenAPI。
- 代码包位于 `com.admin.template`，主要目录为 `controller`、`service`、`mapper`、`entity`、`dto`、`security`、`config`、`common`。
- AI 对话统一使用会话 SSE 接口 `/v1/ai/conversations/**`。

不要引入 JPA Repository、Hibernate Entity、Kotlin 或其他 ORM 风格来替代现有 MyBatis-Plus，除非用户明确要求架构迁移。

## 3. 分层与依赖方向

依赖方向固定为：

```text
Controller -> Service -> Mapper -> Database
                 |
                 +-> 外部服务客户端（如 AI 服务）
```

### Controller

- 只负责路由、HTTP 参数绑定、`@Valid`/`@Validated` 校验、认证用户获取和响应状态码。
- 每个接口调用一个明确的 Service 入口；不直接注入 Mapper，不写查询、事务或权限计算。
- 不返回 Entity；使用请求 DTO、响应 DTO 或明确的分页 DTO。
- 不在 Controller 中捕获通用异常；业务异常交给统一异常处理器。
- 公开接口必须有 `@Tag`、`@Operation`、请求/响应字段说明和必要的参数约束。

### Service

- 承担业务规则、权限相关业务判断、数据编排和事务边界。
- 写操作的 `@Transactional` 放在 Service；外部 HTTP 调用不要放进不必要的长事务。
- 通过构造器注入依赖；不使用字段注入。
- 不返回 `HttpServletRequest`、`HttpServletResponse` 或 `ResponseEntity` 作为业务结果。
- 复杂 Entity 到 DTO 的转换使用 DTO 工厂方法或独立 Mapper，不能让 Controller 和 Service 各自维护一套字段映射。

### Mapper

- 只负责 MyBatis-Plus 数据访问、投影和参数化 SQL。
- `@Select` 等原生 SQL 可以用于明确的投影查询，但必须绑定参数，不得使用用户输入的 `${}` 或字符串拼接。
- 不在 Mapper 中放权限、状态机、错误码或事务业务规则。

### DTO、Entity 与 Map

- 新增请求/响应优先使用 Java `record`；请求校验注解放在请求 DTO 上。
- Entity 只表示数据库持久化模型，不作为公共接口模型。
- 新接口禁止使用 `Object`、`Map<String, Object>` 表示稳定的业务响应；使用有字段定义的 DTO。
- 修改既有接口时保持旧字段名、类型、包络和可空性，除非用户明确批准契约变更。

## 4. HTTP 与接口契约

- 业务接口使用 `/v1` 前缀，资源名使用复数；保留当前路由和前端约定。
- `/v1` JSON Controller 必须显式返回 `Result<T>`；禁止依赖 `ResponseBodyAdvice` 自动包装裸 DTO、Map 或集合。
- 成功和错误 JSON 使用同一个响应模型：`code`、`data`、`message`、`success`、`traceId`、`timestamp`、`details`。成功响应使用数字 `code=0`、`success=true`、`details=null`；业务错误使用数字业务码、`success=false`、`data=null`，`details` 放置可安全返回的错误详情。
- 业务异常、鉴权失败、参数校验失败和限流统一使用 HTTP 200，并通过 `success`、独立数字业务 `code` 表达结果，不以 HTTP 状态码充当业务码。HTTP 协议错误（如 JSON 格式错误、路由不存在、方法/媒体类型不支持）保留真实 HTTP 状态码，响应体 `code` 使用对应状态数字；服务器/外部服务故障保留真实 HTTP 状态码和独立系统错误码。
- HTTP 成功状态约定：查询/更新为 200，创建为 201，删除为 204 且无响应体。系统内部错误和 AI 外部服务失败分别返回 HTTP 500/502。
- 业务异常使用不包含 HTTP 状态的 `BizException` 与 `BusinessError`；全局处理器统一返回 HTTP 200。文件或 AI 系统故障使用 `AppException` 与 `SystemError`。安全过滤器在进入 MVC 前直接写鉴权失败时也使用 HTTP 200 和同一 `Result` 模型。
- 204 响应不得有响应体。
- SSE 流式接口使用 `text/event-stream`，不得包裹为 `Result<T>`；流开始后错误通过 `event: error` 返回，客户端不能只依赖 HTTP 状态判断流是否成功。
- `/v1` JSON 响应必须保留请求追踪 ID；不要在业务代码中重新生成或覆盖已有 `X-Trace-Id`。
- OpenAPI 必须反映真实字段、媒体类型、必填约束和 `Result<T>` 响应包络。当前项目不自动声明 `bearerAuth`，不要把 Authorization 变成查询参数或请求体字段；运行时认证仍从 HTTP `Authorization` Header 读取。
- 修改接口时至少同步检查对应 Controller、DTO、OpenAPI 测试和 README 接口表。

### HTTP 状态码与数字业务码

业务失败的 HTTP 状态始终为 200；客户端根据 `success` 和独立数字 `code` 判断业务结果。协议错误和服务器故障仍以 HTTP 状态码表达。不要依赖可能调整的中文 `message` 做分支判断。业务码在 `BusinessError` 中集中定义，发布后不得重用或随意变更；枚举名仅用于代码和日志，不是响应码。

| HTTP 状态码 | `Result.code` | 使用场景 |
| --- | --- | --- |
| 200 / 201 | `0` | JSON 接口成功 |
| 200 | `100001` | 字段校验、参数类型或上传限制不通过 |
| 200 | `100002` | 登录限流，同时返回 `Retry-After` |
| 200 | `110001` / `110002` / `110003` | 登录凭证错误、Token 无效、账号禁用 |
| 200 | `110004` / `110005` / `110006` / `110007` | 无权限、缺少认证、未分配角色、未分配菜单权限 |
| 200 | `110008` / `110009` / `110010` / `110012` / `110013` | GitHub 未启用或配置不完整、授权失效、取消授权、绑定冲突、仅有 GitHub 登录方式不可解绑（`110011` 保留，不再使用） |
| 200 | `120001` / `120002` / `120003` | 用户不存在、用户名已存在、不能删除自己 |
| 200 | `130001` / `130002` / `130003` / `130004` | 角色代码重复、角色不存在、系统角色受保护、角色正在使用 |
| 200 | `140001` / `140002` / `140003` / `140004` | 菜单 ID 重复、菜单不存在、父菜单不存在、菜单有子菜单 |
| 200 | `150001` | 文件不存在 |
| 400 / 404 / 405 / 406 / 415 | 对应 HTTP 数字 | 请求格式、路由、方法或媒体类型错误 |
| 500 | `500000` / `150101` / `150102` | 未预期的内部错误、文件上传或删除故障 |
| 502 | `160001` | 外部 AI 服务连接、超时或响应异常 |
| 502 | `170001` | GitHub 外部服务连接、超时或响应异常（安全结果在授权完成接口返回） |
| 204 | 无响应体，无 code | 删除成功 |

业务层通过 `throw new BizException(BusinessError.USERNAME_EXISTS)` 抛出异常；全局处理器输出枚举的数字码。字段校验详情使用 `path`、`message`、`type`，其中 `type` 是字段错误类型，不是业务码。Controller 创建仍可使用 `@ResponseStatus(HttpStatus.CREATED)`，删除继续使用 204 且不创建 `Result`。

## 5. 认证、权限与安全

### P0

- 受保护接口使用 `Authorization: Bearer <token>`；Token 不得出现在 URL、请求体、普通日志、异常详情或测试输出中。
- 新增 `/v1` 路由默认需要认证。公开路由必须在 `SecurityConfig` 中显式列出，并同步检查 `JwtAuthenticationFilter`，避免“配置放行但过滤器拦截”或“新增接口默认公开”。
- 需要业务权限的接口使用现有 `@Permission` 和 `PermissionService` 规则；不得只检查前端传入的角色或权限字段。
- 不记录密码、JWT、数据库密码、AI 密钥或完整外部请求头。认证失败日志只记录错误码、方法、路径和请求 ID。
- 新代码不得明文保存或比较密码。当前仓库保留旧系统明文密码兼容逻辑，这是已知迁移债务；涉及登录或用户创建时必须明确说明，不得扩展该模式。
- 不把登录、退出、禁用用户或角色变化的安全语义偷偷改变；需要让旧 Token 失效时，先设计兼容方案和测试。
- 文件上传和删除必须限制在配置的公开目录内，拒绝路径穿越，并执行数量、大小和 MIME 校验。
- 通用公共文件上传、批量上传和删除（`/v1/files`、`/v1/files/batch`）均要求 `system:file:manage` 管理权限，在文件操作前通过现有角色菜单权限查询校验；普通注册角色不得默认获授。权限由系统用户管理下的公开文件管理按钮菜单配置；RAG 文档上传沿用自身知识库权限边界。

### P1

- 权限规则只能有一个业务来源；新增权限判断前先检查 `AuthService`、`PermissionService` 和菜单服务是否存在重复逻辑。
- GitHub 首次授权仅按平台稳定 ID 创建独立普通账号：随机用户名，昵称取 GitHub 登录名，密码为 NULL，复用已有启用的 `user` 角色，不通过名称或邮箱合并账号、不在应用内创建或提升角色。用户、角色关系、绑定及登录权限检查必须处于同一事务，并发身份唯一键失败须先回滚再解析已有绑定；已有绑定的账号状态和权限检查不得绕过。
- 密码登录必须显式拒绝 NULL 密码，不能把它转换成字符串 `null`；无密码或空白密码账号不得解绑 GitHub 唯一登录方式，返回 `110013`。已有密码兼容行为保持不变。
- 外部 AI 请求只转发服务端确认的用户身份，不信任客户端传来的 `X-User-Id` 或 `X-Username`。

## 6. 数据库、事务与性能

- 所有写入操作必须有清晰的事务边界；事务失败不得吞掉异常后继续返回成功。
- 查询条件、排序和分页参数必须经过白名单或范围校验；分页默认值和上限必须明确。
- 列表和导出不得新增逐条查询（N+1）；需要关联数据时优先批量查询或投影。无法避免时在变更说明中写出原因和数据量边界。
- update/delete 必须有明确条件；禁止没有 where 的破坏性 SQL。
- 数据库字段、索引或表结构变化不能只改 Entity；必须说明迁移方式。当前项目不自动执行建表或迁移，不得悄悄依赖启动时建表。
- 时间使用 `java.time` 类型并明确时区；项目持久化时间按现有 UTC 约定处理。

## 7. 测试与验证

- 业务规则优先写 Service 单元测试；Controller 变更写请求级或 MockMvc 契约测试；安全、OpenAPI、文件上传和 AI 转发属于边界契约，必须覆盖成功和失败路径。
- 测试必须可重复，不依赖开发者本机 MySQL、正在运行的 AI 服务或真实网络。AI 外部 HTTP 使用本地测试服务器或明确的测试替身。
- 测试代码也遵守项目契约，认证请求使用 `Authorization` Header，JSON 错误断言错误码和状态码，不断言随机请求 ID 的固定值。
- 使用 JDK 21（运行前确保 `JAVA_HOME` 指向 JDK 21）：

```powershell
mvn -ntp test
```

- 小改动先运行相关测试；完成前运行 `mvn -ntp test`。若无法运行，必须说明具体原因和未验证范围。
- 测试通过不代表真实 MySQL 已验证；当前项目没有真实 MySQL 集成测试 profile，涉及 SQL 或索引时要明确这个限制。

## 8. AI 修改工作流

1. 读取本规范、README、构建配置和目标代码；检查 `git status` 与相关 diff，保留用户已有修改。
2. 搜索被修改方法的调用方、测试、配置和接口文档，确认影响范围。
3. 先写或更新能复现目标行为的测试，再做最小实现；纯文档或配置变更可免除测试，但仍需验证格式和加载路径。
4. 遵循现有模式，不为了引入规范而添加新框架、抽象层或依赖。
5. 修改公开契约时同步 DTO、Controller、OpenAPI、测试和 README；修改安全规则时同步生产配置和安全测试。
6. 完成后运行验证命令，查看 diff 和 `git diff --check`，再报告结果。

## 9. 遗留代码处理策略

- 不因一次普通需求重命名、全量格式化或重写无关类。
- 存量代码的问题分为“本次必须修复”和“已知债务”。只有 P0 安全/数据风险，或直接影响本次改动正确性的债务，才在本次一起处理。
- 当前已知债务包括：旧账号密码存储兼容、部分列表映射可能产生额外查询、少数既有接口仍使用 Map 返回。JWT 已在每次请求校验账户状态、删除状态和退出时间；AI 不得假装其他问题已经解决，也不得在没有迁移方案时单独改动其行为。
- 如果规范与用户明确的业务契约冲突，先保留业务行为并报告冲突；不得静默改变客户端可见行为。

## 10. Definition of Done

一次 Java 后端改动只有同时满足以下条件才算完成：

- 分层和依赖方向正确，未引入新的安全红线。
- 输入、权限、异常和外部调用边界有处理。
- 公共 DTO、响应、状态码和 OpenAPI 与实际行为一致。
- 相关测试已新增或更新，且在 JDK 21 下通过。
- `mvn -ntp test`（适用时）和 `git diff --check` 已执行。
- 结果说明包含文件、测试结果、未处理债务和部署/重启要求。
