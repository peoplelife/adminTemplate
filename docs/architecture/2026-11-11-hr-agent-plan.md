# HR Agent 规划记录

日期：2026-11-11。状态：需求讨论记录，未开始实现；本文件不是已定稿的详细施工计划。

## 目标

在现有项目中提供辅助招聘人员理解岗位、梳理候选人证据和准备面试的 Agent。它可以根据用户目标与工具结果选择下一步，遇到信息缺口主动澄清，而非要求用户完成固定表单流程。

## 业务主线

理解岗位与澄清要求 → 结构化 JD → 结构化候选人经历 → 提取岗位相关 Evidence → 分析能力覆盖 → 发现人工确认问题 → 生成面试建议 → 辅助招聘流程推进。

这条主线是业务参考，不是每次必须执行的固定节点顺序。Agent 根据当前目标决定读取 JD、解析简历、提取证据、提出澄清或生成报告；用户可补充资料、修正解释、要求重新分析。

## 已讨论的需求

1. 岗位画像：明确核心职责、必备项、加分项、期望能力水平及评价依据；模糊或矛盾的要求先向招聘人员确认。
2. 候选人画像：结构化项目、职责、实际贡献、技能与时间线，不生成未经材料支持的经历。
3. Evidence：每项判断可定位原文和来源；区分明确经历、仅技能自述、暂无证据、存在矛盾。没有提及不等于没有能力。
4. 能力覆盖矩阵：展示岗位要求、候选人证据、当前判断、待验证问题；首版不依赖单一综合匹配分。
5. 面试建议：问题绑定岗位能力或证据缺口，包含验证目的、具体问法、追问路径和观察要点，避免通用题库堆叠。
6. 面试后更新：后续支持导入面试记录，新增证据并更新能力矩阵；具体回答与主观评价分开保存。
7. 人工决定：Agent 提供分析、建议和流程草稿；录用、淘汰以及对外沟通由招聘人员决定并确认。
8. 信息边界：聚焦岗位相关资格和经历，不通过姓名、照片、性别、年龄等推断能力或人格；明确简历与面试记录权限、保存期限和删除机制。

## 与现有工程的关系

- 前端：AI 下的对话工作台，岗位、候选人、证据矩阵和报告作为工作区；复用现有组件规范。
- Java：继续负责 JWT、权限、用户身份、接口契约和 AI 网关。
- Python：复用公共文档解析、LLM、default_model、Prompt、日志与数据库；实现 HR 能力和受限工具调用循环。
- API DTO 放 app/schemas，接口业务编排放 app/services，能力实现放相应能力目录，实体与仓储沿用现有位置。
- Python 业务数据仍使用 PostgreSQL public 和 Alembic，不新增 HR 专属数据库、schema 或 settings。
- 不直接套用 RAG 会话或知识库的数据关系；哪些现有能力可复用需实施前核对调用和契约。
- LangGraph、Worker 是否引入及具体职责，待工具、任务时长和恢复要求确认后决定，不为了使用框架增加空模块。

## 交付阶段

- [ ] P0：确认招聘人员使用场景、岗位/候选人资料来源、协作与数据权限。
- [ ] P1：单岗位 + 单候选人，提供岗位澄清、Evidence、能力矩阵、定制面试建议；对话支持澄清和纠正。
- [ ] P2：加入面试记录和人工反馈，更新证据与分析，保留来源和修订记录。
- [ ] P3：对接招聘流程状态、待办和沟通草稿；对外动作单独确认。

## 验收方向

- 准备经授权或合成的 JD、简历和人工标注证据，验证原文定位、提取准确性与遗漏情况。
- 缺失经历应返回暂无证据，矛盾信息应待澄清；不得编造个人贡献或把不确定判断写成事实。
- 面试问题能对应岗位要求与具体证据缺口，用户修正后建议同步更新。
- 工具结果影响 Agent 下一步；信息不足主动询问，不能用固定流程演示代替 Agent 行为验收。
- 用户隔离、删除、模型失败及刷新恢复需在实施计划中加入具体测试。
